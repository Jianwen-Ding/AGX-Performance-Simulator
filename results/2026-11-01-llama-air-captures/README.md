# llama.cpp kernels on the AIR route: simulator vs hardware (2026-11-01)

12 launches captured from llama.cpp b11706 (Qwen2.5-0.5B Q5_K_M, `-b 8 -ub 8`) running on zluda_agx's AIR route
(ZLUDA claude/perf-air-agx): the 12 kernels with the most GPU time, each after its 50th launch
(`ZLUDA_AGX_CAPTURE_SKIP=50`). Each is replayed on the GPU (`agx_run_hw --back-to-back N`) and in `agx_dispatch`
with its real memory (`scripts/capcheck.py`). Captures themselves (2 GB) are not kept: they are regenerated by the
command in `capcheck.py`'s docstring.

| Run | Median abs. error | Within 10% | Within 25% |
| --- | --- | --- | --- |
| hardware 30 back to back, launch profile drm (`capcheck-base.txt`) | 35% | 0 / 8 | 1 / 8 |
| hardware 1000 back to back, drm (`capcheck-warm.txt`) | 27% | 2 / 8 | 4 / 8 |
| 1000 back to back, `--launch-profile zluda` (`capcheck-warm-zluda-profile.txt`) | 27% | 1 / 8 | 3 / 8 |
| the same with the cold instruction fetch (`capcheck-warm-zluda-fetch.txt`) | 21% | 2 / 8 | 5 / 8 |
| hardware the median of 5 runs, stack kernels replayed with their stack and the stack setup modelled (`capcheck-repeat5.txt` + `--stack`) | 21% | 3 / 10 | 7 / 10 |
| **ZLUDA's current code** (private arrays in registers; captures with the next allocation), the same 12 kernels recaptured (`capcheck-current-build.txt`, type 13: -18%) | 18% | 3 / 12 | 11 / 12 |
| the same with the store bandwidth floor (zluda profile) | 16% (11 + type 13 -18%) | 3 / 12 | 11 / 12 |
| and the 0.7 us of a kernel that writes (`capcheck-current-build-sim-final.txt`; type 13 -17%) | **8%** | 7 / 12 | 11 / 12 |

- **Measure at a warm clock.** 30 launches back to back do not ramp the GPU's clock: the Q8_0 matrix-vector kernel
  (the largest, 2 waves of 12 workgroups per core) measured 67 us after 30 and 26.2 us after 1000; the simulator
  says 28.4 us (drm profile) / 25.1 us (zluda profile), -4%.
- **Launch cost of zluda_agx's commands** (`launch-cost.txt`, an empty kernel, `stop`): 2.3 us fixed back to back
  (3.8 us isolated), ~100 ns per workgroup per core, independent of the SIMD groups per workgroup (32 or 1024
  threads) and of the register allocation (8-256 halves); the drm profile's 5.6 us and 13.6 ns per SIMD group come
  from the direct-DRM harness's commands. `--launch-profile zluda` predicts the empty dispatches within 3-22%.
- **Open: tiny single-wave kernels are predicted too fast once launch costs are right** (-18% to -60%: rope 8.5 us
  hw / 3.4 sim, set_rows 6.5 / 3.1, quantize_q8_1 4.3 / 3.2). The hardware time beyond the launch cost (2-6 us) is
  not explained by code size (660-1280 bytes), mapped memory size (an empty kernel with 0-512 MiB mapped: the same
  2.3 us), the cold start the model already applies (first touches from DRAM), or page walks (a new page per
  dependent load costs +8 ns over a new line: playground 2026-11-01-first-touch-pages). Next: trace one (set_rows)
  and time its instructions in isolation.
- **Cold instruction fetch**: straight-line code (`line*.ptx`, one thread, 16-1024 fma) costs ~104 ns per 64-byte line
  at the start of every command (294 -> 4134 bytes: 2.79 -> 9.04 us), which the model lacked (2.4 -> 2.7 us). The
  zluda profile counts the distinct lines the first wave executes and takes the slower of fetch and execution
  (they overlap: added in full, the Q8_0 kernel's 138 lines made it +50%): the straight-line kernels within 1-3%.
- **Open: the fetch term overestimates mad chains** (`mad-chains.txt`: one thread, dependent `mad.lo` chains;
  mad32 512: 7.0 us hw, 9.1 sim; mad64 512: 25.8 / 35.7): ~60-73 ns per line there against 104 for the fma kernels, at
  the same ~8 instructions per line, so the cost is not per line alone. A two-term fit (16 ns a line + 5.5 ns an
  instruction) matched the mad chains but missed line1024 (6.2 against 9.0 us) and made the captures' median 25%:
  reverted. Short single-thread runs also vary run to run (mad32_64: 3.8 and 4.8 us).
- **A single hardware measurement of a tiny kernel is not a reference**: the same replay of set_rows gave 6.5 us once
  and 3.9-4.3 in five later runs, rope 5.6-8.7 us (bimodal), rms_norm 5.1-5.25. `capcheck.py --hw-repeat 5` takes the
  median; with it set_rows is -16%, rope -24/-26%.
- **A kernel with a stack costs ~7.5 us more per command** (`stack-launch.txt`: an empty kernel, 38 to 15,200
  workgroups, +7.1-8.1 us with `--stack 64`): the scratch set up at the launch. Modelled (zluda profile,
  `agx_dispatch --stack`); llama.cpp's mul_mat_vec_f kernels -72% -> -56%, -39% -> -25%. ZLUDA then kept their
  small array in registers (no stack: 46.1 -> 14.6 us and 53.8 -> 25.3 us on the GPU); on that code the simulator is
  -19% (11.8 us) and +13% (28.6 us): most of the old gap was the scattered stack traffic.
- **Stores cost bandwidth even when they fit the system-level cache** (`st.ptx`, `stn*.ptx`: 1520 x 256 threads
  writing 1.5 / 6 / 24 MB, hw 9.9 / 22.0 / 72.1 us; the model had 6.3 / 6.9 / 73.8, the cache absorbing the smaller
  ones): ~365 GB/s, after the workgroups' launch. zluda profile `store_gbps`: 10.6 / 23.4 / 74.5 us.
- **A kernel that writes costs ~0.7 us more per command** than the empty one (one workgroup storing 1 KB: 3.0 against
  2.3 us), now in the zluda profile (`store_launch_ns`). The fetch benchmarks, which write their result, were fitted
  without it: line1024 is +8% with it.
- 4 captures (`mul_mat_vec_f` x2, `mul_mat_vec_q` type 13, type 7 with 1 column) do not replay: the GPU faults
  ("Bad address") or the parameter block's fixed address is taken. Their captures miss memory the kernels reach
  (pointers inside by-value structs such as ggml_cuda_mm_fusion_args_device): a capture bug in zluda_agx, not
  replayed again until fixed (each failure is recorded in the GPU safety budget).
